# 项目复盘案例：公开知识产权数据实体匹配项目

> **业务线**：量潮数据（数据工程项目） ｜ **周期**：分阶段交付 ｜ **状态**：已完成基础交付，持续沉淀复现经验
> **角色**：商务经理、软件工程师、数据复核人员

**案例标识**：外部学术研究类数据工程项目；从公开知识产权数据中提取实体名称，关联到标准实体目录；项目同时包含历史实现复现、批量匹配和结果审核。

---

## 一、项目概况

**交付范围**：

- 加载公开知识产权记录，保留实体名称及必要的上下文信息。
- 对原始实体名称进行清洗、标准化和统一格式处理。
- 将标准化后的实体名称匹配到外部提供的标准实体目录。
- 输出原始名称、标准化名称、关联实体标识、匹配类型、置信度和来源说明。
- 对低置信度和无匹配结果进行分级审核，并交付结果文件、处理脚本和逻辑说明。

**验收标准要点**：

- 原始记录能够回溯到匹配结果。
- 标准化规则稳定，正常的多行重复记录不能被误判为数据错误。
- 匹配结果需要区分直接命中、近似命中、低置信度和无匹配。
- 多个来源的结果需要保留来源标记。
- 大规模数据处理需要能够在合理时间内完成，并保留可复现的运行方式。

## 二、项目过程

| 阶段 | 事件 |
|---|---|
| 需求确认 | 明确公开数据、标准实体目录、匹配结果和审核结果的基本范围 |
| 数据准备 | 整理原始数据包和标准实体目录，检查文件结构与字段对应关系 |
| 方案设计 | 将旧实现的处理逻辑拆分为数据加载、名称标准化、匹配、审核和导出几个阶段 |
| 初次复现 | 使用命令行数据工程工具生成需求文档、契约、规格和处理脚本 |
| 真实数据运行 | 小样本运行暴露参数、字段、映射表格式和结果数量方面的问题 |
| 规则修正 | 补充模糊匹配、候选索引、名称去重、置信度分级和结果回填逻辑 |
| 交付复核 | 检查结果文件、来源标记、审核状态和运行日志，形成可复用的复现记录 |

## 三、复盘发现

### 沟通与流程

**数据契约没有足够前置**：

- 原始数据中的实际字段与自动生成脚本预设的通用字段并不完全一致。
- 标准实体目录的文件格式、列名和唯一性约束没有在第一版规格中写清楚。
- 结果字段、匹配顺序和多来源处理方式如果只停留在自然语言层面，后续生成脚本容易自行发挥。

**验收标准需要用样例表达**：

- “匹配成功”不能只用是否存在结果判断，还要同时检查匹配类型、置信度、来源和原始记录回填。
- 同一实体名称在源数据中出现多行是正常业务现象，不能把源记录重复和匹配目录重复混为一谈。
- 低置信度结果是否进入人工或模型审核，需要在方案阶段明确。

**资料依赖没有单独登记**：

- 标准实体目录是流程能否继续的关键输入，缺失时应在任务启动阶段明确登记。
- 数据包、映射目录、运行参数和交付结果需要分别记录，不能只保留一个最终文件。

### 实操（技术）

**名称标准化是匹配的前置门槛**：

- 需要处理大小写、标点、空格、法律实体后缀和常见写法差异。
- 标准化后的名称用于建立候选索引，但不能取代原始名称。
- 每条源记录仍需要保留自己的稳定行标识，不能用实体名称作为唯一键。

**匹配算法不能停留在等值连接**：

- 只做严格等值匹配时，结果数量可能很少，但程序不一定报错。
- 真实数据需要先标准化，再通过候选索引缩小范围，最后进行近似匹配和置信度分级。
- 匹配结果生成后还要回填到原始记录，避免只交付去重后的候选表。

**性能问题会在全量运行时放大**：

- 逐行扫描全部候选目录在小样本上看不出问题，放大后会显著变慢。
- 应先对候选目录去重并建立索引，再进行批量匹配。
- 全量运行前需要完成小样本冒烟测试，检查行数、命中类型分布和审核状态，而不只是检查是否生成了文件。

**命令行产物需要人工验收**：

- 自动生成脚本的参数名称、输入方式和输出格式可能变化。
- 运行前必须查看帮助信息，并先做语法检查。
- 契约、规格和生成脚本都需要检查关键字段是否被保留，不能只看命令是否返回成功。

**审核接口需要被当作工程依赖管理**：

- 审核阶段需要明确接口地址、模型名称、鉴权方式、单次审核数量和失败回退方式。
- 应支持跳过审核和限制审核条数，避免一次运行发送过多请求。
- 网络失败、鉴权失败和响应格式错误都应写入结果意见，不应悄悄覆盖原始匹配结果。

## 四、沉淀的改进方向

| 方向 | 具体措施 |
|---|---|
| 数据契约前置 | 先建立输入文件、字段、类型、唯一性和缺失值规则，再生成处理规格 |
| 结果口径明确 | 用正例、反例和边界例说明直接命中、近似命中、低置信度和无匹配 |
| 算法分层 | 标准化、候选索引、近似匹配、置信度分级和审核分别作为可检查步骤 |
| 性能门槛 | 先运行小样本，再检查候选规模和耗时，确认后再进入全量处理 |
| 运行方式固定 | 生成脚本后立即检查帮助信息、语法和输入输出参数，记录实际命令 |
| 依赖可追踪 | 单独登记标准实体目录、模型审核接口和其他外部依赖的状态 |
| 结果可回溯 | 保留源记录行标识、原始名称、标准化名称、候选结果、审核状态和来源 |
| 失败可解释 | 将缺文件、参数错误、映射表格式错误、网络错误和鉴权错误分别记录 |

## 五、案例启示（对内）

- **实体匹配项目首先是口径项目**：字段、唯一性、匹配顺序和审核边界没有写清楚，代码越快生成，返工越快发生。
- **等值匹配能运行不代表匹配有效**：需要同时检查命中规模、置信度分布、无匹配比例和样本抽查结果。
- **源数据重复不等于数据错误**：要区分业务记录的多行出现、标准化名称重复和候选目录的唯一性要求。
- **全量处理前必须做冒烟测试**：小样本要验证业务结果和运行性能，不能只验证文件是否存在。
- **命令行生成链需要产物检查**：需求、契约、规格和代码各自通过，不等于最终管道语义正确。
- **审核服务是可失败的外部依赖**：接口不可用时要保留匹配结果和失败原因，不能把审核失败伪装成匹配结论。
