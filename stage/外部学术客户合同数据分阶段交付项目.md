# 项目复盘案例：外部学术客户合同数据分阶段交付项目

> **业务线**：量潮数据（数据工程项目） ｜ **周期**：多个交付阶段 ｜ **状态**：年度资料已整理，管理档案待持续维护
> **角色**：项目管理、软件工程、商务和数据复核

**案例标识**：外部学术客户的合同数据项目；基于公开申报材料识别融资合同；分阶段完成样本验证、规则修正和年度交付；后续增加企业经营关系信息抽取。

---

## 一、项目概况

**交付范围**：

- 从公开申报材料中识别融资合同、修订件和延期件。
- 排除债券类文书、公告、法院材料、目录和其他非目标文件。
- 从目标合同中提取企业经营关系相关句子。
- 对年度交付包进行人工复核、重新整理和交接归档。

**交付物**：

- 目标合同原始材料包。
- 企业、合同和句子层级的结构化数据。
- 文件范围、分类理由和处理统计。
- 面向客户的交付说明和复核说明。

**验收标准要点**：

- 主合同、修订件、延期件和补充件分别归类。
- 非目标文书不能因为正文提到融资或担保词语而被误收。
- 经营关系句子需要描述真实的供应商、客户、分销、产品或业务关系。
- 法律定义、担保条款、金融机构模板和目录文字不作为经营关系信息。
- 每条结构化结果都能回到对应合同和原始位置。

## 二、项目过程（关键节点）

| 阶段 | 事件 |
|---|---|
| 需求确认 | 客户先要求完成一个中间年度样本，用于验证合同识别口径 |
| 样本交付 | 团队交付第一批样本，客户抽检后发现少量非目标文书被误收 |
| 规则修正 | 团队重新区分主合同、补充件和非目标文书，收紧标题与上下文判断 |
| 分析扩展 | 客户进一步确认需要从合同中识别企业经营关系信息 |
| 复核迭代 | 团队增加候选句子筛选和人工复核，排除法律模板与金融机构噪声 |
| 年度交付 | 后续年度资料按统一结构重新整理，保留索引、统计和交付说明 |
| 交接归档 | 项目资料、代码版本、客户过程和待办事项被拆分登记到不同管理入口 |

## 三、复盘发现

### 沟通与流程

**需求边界没有一次性固化**：

- 初始需求只说明要找“融资合同”，但没有充分定义主合同、补充件、修订件和相关文书的边界。
- 客户通过抽检结果逐步补充例外情况，团队再把这些例外转为规则。
- 经营关系信息的判断标准也经历了从关键词命中到业务事实判断的变化。

**验收标准形成得太晚**：

- 文件范围、排除规则和句子质量要求分散在聊天、附件和样例中。
- 团队在收到客户反馈后才把部分口径写进处理逻辑和复核表。
- 这使得前期交付容易出现“技术上完成，但客户认为口径不对”的情况。

**资料入口不够统一**：

- 代码、年度交付包、客户沟通和商务信息分散在不同位置。
- 年度压缩包中曾保留本机目录前缀，解压后不利于新人查找。
- 稳定版本和一次性修复脚本没有一开始就分开标识。

### 实操（技术）

**分类规则需要按文书语义分层**：

- 只看正文关键词会把公告、风险说明或担保模板误判为目标合同。
- 标题、文书类型、合同主体和上下文需要联合判断。
- “修订件中包含补充加入条款”与“纯补充加入文书”不能使用同一分类。

**经营关系抽取不能只靠词语匹配**：

- “供应商”“客户”“库存”等词语可能出现在法律定义、担保条款或金融机构模板中。
- 需要先做候选筛选，再判断句子是否描述客户企业自身的业务事实。
- 每条结果都应保留可回溯的位置和来源关系。

**交付修复工具与主流程发生耦合**：

- 年度复核过程中产生了大量针对特定阶段的修复脚本。
- 一次性日期修复逻辑被主流程直接引用，导致干净环境难以复现。
- 工作区处于分离版本且有未提交修改，正式版本边界不够清晰。

**外部模型调用增加了数据治理要求**：

- 对边界样本或候选句子的自动判断可以减少人工工作。
- 但合同文本属于客户项目资料，启用外部模型前必须确认授权、数据传输范围和费用归属。

## 四、沉淀的改进方向

| 方向 | 具体措施 |
|---|---|
| 需求澄清前置 | 先制作“文书分类口径单”和“经营关系判断口径单”，每类配正例、反例和边界例 |
| 样本验收前置 | 先用小批量样本确认分类和抽取结果，再扩大处理范围 |
| 交付结构统一 | 每个阶段固定保留原始材料、结构化结果、索引、统计和说明五类内容 |
| 版本边界清晰 | 通用主流程、年度修复工具和临时输出分开维护，版本发布前做干净环境验证 |
| 数据资产沉淀 | 保留数据来源说明、处理口径、复核依据和结果索引，避免下一次交接重新猜测 |
| 质量可追溯 | 每条结构化结果保留来源合同、原始位置和复核状态 |
| 外部服务治理 | 对外部模型调用建立授权检查、脱敏规则、费用记录和失败回退机制 |
| 管理档案分层 | 项目管理案例只放脱敏叙事，完整客户资料放在受控项目资料库 |

## 五、案例启示（对内）

- **合同数据项目的第一交付物不是数据，而是口径**：如果主合同、补充件和非目标文书没有用例子对齐，后续规模越大，返工成本越高。
- **关键词命中不等于业务事实**：经营关系抽取必须区分真实业务叙述和法律模板。
- **阶段性修复不能替代正式版本管理**：修复脚本有价值，但必须明确它服务于哪一批交付、是否可复用，以及是否已经纳入主流程。
- **项目交接需要三张地图**：项目地图说明目标和状态，资产地图说明代码和数据在哪里，决策地图说明为什么采用当前口径。
- **公开案例与内部档案必须分层**：公开案例保留方法和教训，客户细节、合同和原始数据进入受控资料系统。
